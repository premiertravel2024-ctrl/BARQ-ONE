# BARQ v2.19.0 — إعادة تنظيم العقل واستقبال الأوامر والتعافي

28 أكتوبر 2026. حزمة سورس كاملة مبنية على v2.18.3. لا تتضمن EXE أو مثبتًا جديدًا جرى التحقق منه على Windows هنا.

## النتيجة

أُعيد تنظيم الطريق من رسالة المستخدم إلى فهم الهدف وحفظه وتجهيز خطوة فعلية ومراجعة أسباب التوقف. التصحيح يعالج أسبابًا داخل التطبيق أمكن إعادة إنتاجها؛ لا يضمن توافر خدمات المزودين أو فهمًا مثاليًا لأي جملة. توليد برنامج مخصص كامل يحتاج نموذجًا متاحًا، وأدوات فعلية، وبيئة اختبار مناسبة. إنشاء هيكل أولي ليس اكتمال البرنامج.

## الأسباب التي عُثر عليها

1. كان اكتشاف سؤال الإمكانية يبحث عن «ممكن» و«هل» وألفاظ أخرى في كامل الرسالة، فشرط جانبي داخل مواصفات مشروع واضح قد يمنع التعرف المحلي على طلب البناء. وكان شرط «شرح» يلغي نوع إنشاء التطبيق حتى عندما يقول المستخدم «لا تكتفي بكتابة شرح».
2. كان طلب الفهم الداخلي يُعاد تصنيفه حسب كلمات داخل البيانات التي يفهمها: JSON أو صورة أو أدوات داخل مواصفات البرنامج. هذا قد يستبعد نموذجًا نصيًا قادرًا على الفهم لأن سجل قدراته لا يعلن خاصية JSON الأصلية أو رؤية الصور. أُعيد إنتاج حالة استبعاد النموذج قبل أي HTTP.
3. كان فحص JSON العام يستطيع رفض رد محاط بسياج Markdown قبل وصوله إلى محلل عقد الفهم/الأدوات القادر على استعادته بأمان. بعض حقول الفهم المساعدة كانت إلزامية بلا حاجة؛ صارت لها قيم افتراضية، مع بقاء نوع المهمة والهدف وعقد الأدوات والتحقق من المفاتيح المكررة.
4. فشل الفهم كان يتحول إلى نص عام، قبل إنشاء سجل مهمة قابل للاستكمال. لذلك لم تكن هناك بطاقة مرتبطة بالطلب الأصلي وبسبب الفشل.
5. فحص إتاحة النموذج داخل تخطيط المسار كان يستطيع حجز محاولة نصف مفتوحة للتعافي، رغم أن المعاينة لا ترسل طلبًا إلى النموذج. المعاينات المتكررة أو الإلغاء قد تترك نموذجًا مستبعدًا بعد انتهاء الانتظار. كما أن النجاح لم يكن يصفر فترة انتظار قديمة في الصحة.

## التنظيم الجديد

- `/v1/brain/command` هو مدخل الشات الموحد. يحفظ الطلب وسياقه ومجلده ووضع الخصوصية في SQLite قبل استدعاء النماذج. التعرف على طلب واضح هو مسار سريع محلي؛ الصياغات الأخرى تستفيد من الفهم الدلالي وسياق المحادثة والمهمة الحالية.
- الطلبات الواضحة لإنشاء تطبيق، بما فيها طلب TOFU الطويل مع شروطه، تصل إلى خطة إنشاء مشروع أولي دون اتصال بنموذج لمجرد فهمها. الخطة لا تُنشئ ملفات حتى الموافقة. التطوير المخصص التالي يحتاج نموذجًا وأدوات فعلية؛ لا يدعي البرنامج اكتمال التطبيق عند الهيكل الأولي.
- يُفصل الهدف الرئيسي عن الشروط اللاحقة عند التعرف المحلي، مع الاحتفاظ بمتطلبات الطلب كاملة للتخطيط. الأسئلة والأوامر المنقولة وطلبات البرومبت لا تصبح موافقة على إنشاء مشروع. الطلب المنفي لا يسمح بتنفيذ عكسه. كلمات الهوية داخل هدف مشروع لا تحول الأمر إلى تعريف ببرق.
- تمييز طلب إخراج JSON نصي عن احتياج API الأصلي إلى schema: النماذج النصية يمكنها إرجاع JSON يُتحقق منه. يبقى فلتر القدرات الأصلية مفروضًا عند طلبها صراحةً. طلبات الفهم والتخطيط الداخلية تستخدم ملف قدرات نصيًا مناسبًا لغرضها، ولا ترث طلب رؤية من عبارة داخل المواصفات. فلاتر الخصوصية والحصص والمجانية والموديل المختار تبقى فعالة.
- النتيجة المفهومة تحصل على command_id مرتبط بالمحادثة. تجهيز المشروع يستخدم نفس الهدف المحفوظ بدل إعادة تفسير رسالة خطأ من المساعد أو نص مختلف يرسله العميل.
- عند فشل النماذج تصبح الحالة waiting_model، مع بطاقة تعرض سببًا محددًا: مفتاح، حصة، اتصال، صيغة رد، نموذج غير مؤهل، أو فترة انتظار. يوجد زر استكمال للطلب نفسه وزر إدارة النماذج.
- الاستكمال يسترجع الطلب الأصلي حتى بعد إعادة تشغيل العقل وإعادة تحميل الواجهة. الإخفاقات غير مخزنة في ذاكرة قرارات الفهم المؤقتة، فلا يُعاد نفس الرفض من الكاش بعد عودة الخدمة. تبقى فترات الانتظار والحصص الفعلية محترمة.
- الاستكمال مرتبط بالمحادثة والمجلد، ولا يمنح صلاحية تنفيذ أو حفظ. إلغاء الطلب يمنع استعادته بمعرفه القديم، والإلغاء أثناء اتصال النموذج لا يعيد إحياء الطلب. يمكن للمستخدم تقديم طلب جديد بعد الإلغاء.
- النسخة المحفوظة تمر بإخفاء بيانات الاعتماد. تُحفظ ضرورة الوضع المحلي أيضًا، لذلك لا يسمح إخفاء السر من نسخة الاستكمال بتحويل طلب محلي إلى السحابة عند تغيير اختيار النموذج.
- التخطيط ومعاينة المسار يقرآن حالة التعافي دون حجز محاولة. الحجز يحدث عند إرسال الطلب الفعلي، ويتحرر عند الإلغاء، ويزيل النجاح فترة الانتظار القديمة. المحاولات المؤقتة تبقى محدودة وتراعي الحصص، ثم تتاح البدائل المسموحة.
- مسارات Windows تجمع وحدات brain صراحة وتتحقق من وجود ملفاتها الجديدة. الإصدار والواجهة ومدخلات البناء اتسقت على 2.19.0. إصلاحات SQLite وUsePreviousLanguage=no السابقة محفوظة.

الاختبارات الجديدة تشمل طلبًا طويلًا به «ممكن» و«لا تكتفي بشرح» وJSON، وعدة صيغ مصرية وإنجليزية، وأسئلة وأوامر منفية لا تمنح صلاحيات. وتشمل Engine ومحولات مزودي HTTP الفعلية مع httpx.MockTransport: ردود 401 و429 و503، انتقالًا بين Groq وOpenRouter، استعادة JSON محاط بسياج، وفشل جميع النماذج ثم العودة بعد انتهاء الانتظار وإعادة تشغيل العقل. وتشمل حماية المحادثة والمجلد، عدم تحويل الطلب الخاص إلى السحابة بعد إخفاء أسراره، إلغاء أثناء الفهم، وعدم كتابة ملف أو تنفيذ أداة دون الموافقة.

اختبار `scripts/ui_command_smoke.py` يستخدم React المبني والخادم المحلي ومساحة العمل الحقيقية في مجلد مؤقت، مع ردود HTTP مضبوطة للمزودين ومفتاح اختباري. لم يوافق على إنشاء ملفات مشروع أو تعديلها. سجله يثبت أن المصدر لم يتغير، وأن الطلب استُعيد بعد إعادة التشغيل. هذا يختبر سير التطبيق والربط والتعافي؛ ليس قياسًا لدقة نماذج حقيقية أو إثبات نجاح توفو كتطبيق مكتمل. لم تُستخدم مفاتيح المستخدم أو اتصالات نماذج خارجية في هذه الاختبارات.

السجلات في verification/v2.19. ملفات reproduced وattempt وسجلات التحقق الجزئي قد تحتوي إخفاقات متوقعة لإعادة الإنتاج أو محاولات تطوير سابقة؛ المرجع النهائي هو python-tests.log وpython-tests.xml وfrontend-validation.log وbrowser-command-smoke.json وsource-self-test.json. بقي تحذير إهمال Starlette، وتحذير حجم JavaScript، والخط التجاري الاختياري غير المرفق. لم تُخفَ إخفاقات البناء أو الاختبارات.

## طريقة البناء وحدود التسليم

فك الحزمة في مجلد جديد وافتح BARQ وشغّل BUILD_BARQ.bat. بناء React وإعادة تغليف EXE ضروريان؛ إعادة تشغيل ملف قديم أو نسخ Python بجانبه لا يطبقان التغيير. لا تستخدم مجلد staging السابق، ولا تشغّل installer.iss منفردًا، ولا تتجاوز فحص EXE أو اختبار التثبيت.

عند نجاح كل مراحل Windows فقط، تظهر release/BARQ_Setup_2.19.0.exe وBARQ_Portable_2.19.0.zip وbuild-ok-v2.19.0.marker. لا تحذف بياناتك أو مفاتيحك: معرف التثبيت ومسارات البيانات كما هي. هذه حزمة سورس كاملة، لا مثبت Windows مُثبت النجاح. القائمة الدقيقة للملفات مقارنة بـv2.18.3 في CHANGED_FILES.md وCHANGED_FILES.json، والبصمات في SOURCE_MANIFEST_SHA256.json.
