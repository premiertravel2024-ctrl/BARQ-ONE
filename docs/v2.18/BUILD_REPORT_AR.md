## الإصلاحات المنفذة

- حفظ حالة paused ورمز إعادة التخطيط عند تعطل النموذج أثناء الفحص التلقائي أو من أول محاولة؛ لا تختفي إمكانية الاستكمال.
- حفظ نقطة استعادة منقحة في SQLite واستعادة التخطيط بعد إعادة تشغيل العملية. تُستعاد بيانات التخطيط، وتُطلب موافقة جديدة لكل تنفيذ؛ لا تُعاد صلاحيات قديمة تلقائيًا.
- توحيد تحويل نتائج API إلى حالة المهمة بين الكتابة في الشات وبطاقات الموافقة. فشل التخطيط بعد حفظ الملف لا يظهر اكتمالًا.
- الاحتفاظ بإيصال الحفظ عند انقطاع استجابة الاستكمال؛ المحاولة التالية تستأنف التخطيط دون إعادة كتابة الملف. إعادة طلب resume لنفس الإيصال لا تعيد التخطيط داخل نفس الجلسة.
- رفض استهلاك خطة مملوكة لمحادثة أخرى حتى لو حُذف conversation_id؛ الإبقاء على توافق العمليات القديمة المعزولة بمجلد العمل.
- منع إعلان التطبيق مكتملًا بمجرد نجاح فحص أو إنشاء قالب: إنشاء تطبيق يتطلب تغييرات محفوظة وفحصًا بعد آخر حفظ، وطلب EXE يتطلب دليل بناء ناجح. يظل التحقق من اكتمال المتطلبات الوظيفية معتمدًا على الاختبارات والمراجعة؛ لا يُفترض أن اجتياز أي اختبار يثبت كل وظيفة تلقائيًا.
- إتاحة project_build لمنفّذ الشات باستخدام ملفات البناء المعتمدة أصلًا، ودعم تشغيل الاختبارات في مجلد المشروع الفرعي. البناء دون Windows يتوقف بسبب واضح.
- توسيع ميزانية المهمة من 7 إلى 40 جولة، مع إعداد محدود بحد أقصى 100؛ كل عملية تنفيذ حساسة تحتفظ بموافقتها.
- التحقق من الخطط عبر Pydantic Schema، ورفض الحقول المكررة والأنواع الخاطئة وغياب steps والخطط المتعددة. يُسمح بكائن JSON واحد محاط بتعليق؛ لا يتم تجاوز صلاحية الأدوات أو الموافقات.
- إضافة إعادة محاولة محدودة لأخطاء HTTP المؤقتة 500/502/503/504 مع backoff وjitter. تظل الحصص وRetry-After وFree Guard هي القيود الحاكمة، ولا تُفعّل نماذج مدفوعة.
- توحيد مهلات الاتصال والقراءة، وتمرير سياق Ollama التكيفي في الطلبات العادية والمتدفقة. تستخدم الطلبات العادية واجهة Ollama الأصلية حتى يُطبّق num_ctx فعلًا.
- تكييف السياق حسب RAM المتاحة ونمط الأداء وانشغال CPU وحد النموذج؛ أقل الموارد يصل إلى 2048 أو حد النموذج الأصغر. لا يوجد ادعاء بتسريع GPU غير مدعوم.
- جعل تحديثات أحداث المهمة والأدلة ذرية داخل معاملة SQLite؛ اختبار تزامن فعلي يثبت عدم فقد الأحداث.
- إصلاح قراءة Host الخاص بـIPv6، ورفض العملاء غير المحليين وطلبات WebSocket ذات الأصل الأجنبي، وتوسيع حد الطلبات لمسارات التخطيط المكلفة.
- استخراج جرد النماذج إلى api_routes/models.py وإعادة استخدامه في API؛ إظهار سبب عدم جاهزية النموذج في القائمة، والتحقق من priority عند تحميل إعدادات المزود أيضًا.
- إبقاء الشات الأساسي مركز الأوامر، وفصل إشعارات التنقل عن نتائج التنفيذ. لا يؤدي خطأ واجهة أو غياب DOM إلى تحويل خطة صالحة إلى failed. تمر واجهة CLI الآن عبر شخصية Brain المركزية أيضًا.
- تحديث الإصدار في نقطة التشغيل والواجهة والمثبت والسكربتات والـWorkflow مع فحص الاتساق. حافظ التثبيت العادي على معرّفه ومسار البيانات، مع معرّف منفصل لاختبار تثبيت مؤقت دون تعديل تسجيل التثبيت الحقيقي.
- تحديث خط بناء Windows: فحص المصدر، npm ci، Lucide، TypeScript، JavaScript والشات، React، Python، PyInstaller، اختبار الملف المجمد، اختبار المثبت في مجلد مؤقت، Portable، ثم SHA256. الفحوص الجديدة جاهزة للتشغيل ولم تُنفّذ على Windows هنا.
- إخراج وضع الواجهة الاحتياطي تحت release/recovery ومع علامة recovery منفصلة؛ لا يُعامل كإصدار fresh-react معتمد.

## الاختبارات القديمة وما حدث أثناء الفحص

أخطاء decision وLayout المذكورة كانت مُصلحة بالفعل في السورس المرفق؛ مر TypeScript واختبار Node الأساسي قبل التعديل. وُجد build/jobs.py وكذلك حزمة React الأصلية فعلًا، ولم تُعرض هذه الأمور كإصلاحات جديدة.

التشغيل الأول المتوازي لـpytest وVite سجل فشلًا عند قراءة index.html أثناء استبداله، وفشل اعتماد BeautifulSoup غير المثبت. أُعيد الفحص على نسخة أصلية مستقلة مع اعتماديات الاختبار، ونجحت الاختبارات الأصلية الـ695؛ السجل المستقل هو المقارنة المعتمدة. تبقى المحاولات الأولى والسجلات الوسيطة في verification/v2.18/history.

استُبدل اختبار Launch Resolver الذي يفحص عبارات داخل المصدر بتشغيل Node حقيقي يتحقق من التوجيه والتنفيذ والموافقات. أُضيف اختبار يفشل عمدًا للتأكد من أن المشغّل يعيد فشل الطفل دون إخفائه. اختبارات الإصدار تتبع VERSION الحالي بدل تثبيت رقم قديم. استُبدلت فحوص نصية لحالات الشات بفحوص سلوكية تستخدم المسار الفعلي.

اختبار المتصفح القديم كان يشير إلى aria-label قديم وإلى مسار شات سابق، ويتوقع قائمة جانبية في مساحة الهاتف رغم وجود زر الرجوع للشات. صُححت محدداته وبياناته المقلدة مع الإبقاء على فحص فتح مساحة العمل والعودة للمحادثة وعدم وجود شات ثانٍ، وفحص الرد المحلي الحقيقي. لم تُحذف اختبارات فاشلة ولم تُغيّر نتيجة متوقعة لإخفاء خطأ تنفيذ.

## ما بقي غير متحقق أو يحتاج عملًا لاحقًا

1. **Windows غير مختبر:** لا توجد بيئة Windows/PowerShell/Inno متاحة محليًا، ولا مستودع BARQ مطابق ضمن المستودعات المتاحة لإرسال Workflow إليه. لم يُنشأ مستودع ولم يُنشر السورس. لذلك لا توجد روابط GitHub Actions لعملية بناء هذا التعديل، ولا يمكن اعتماد المثبت أو صحة سكربت Inno بتشغيل فعلي بعد.
2. **النماذج الحية:** لم تُختبر مفاتيح Gemini/Groq/NVIDIA/OpenRouter أو نموذج Ollama حقيقي. اختبارات الأعطال والخطط تستخدم مزودين مقلدين؛ اختبارات الملفات وpytest والموافقات وHTTP والمتصفح فعلية. لا يوجد ادعاء بأن أي طلب موسيقى عشوائي سيُنتج تطبيقًا تجاريًا كاملًا دون مراجعة.
3. **مراجعة الواجهة على Windows/WebView2 والتحكم المكتبي والصوت الفعلي:** غير منفذة هنا. اختبار المصدر نجح في HTTP واستيراد WebView، وليس تشغيل نافذة Windows أصلية.
4. **تحذيرات البناء:** حزمة JavaScript نحو 1.46 MB قبل gzip؛ ما زال تحذير حجم الحزمة قائمًا. الخط التجاري GE SS Two غير مرفق؛ يعمل fallback، ويظل نسخ خط المستخدم المحلي مدعومًا. يوجد تحذير إهمال من FastAPI/Starlette لا يفشل الاختبارات.
5. **العمل المعماري تدريجي:** api.py ما زال كبيرًا، ولم يُعد تنظيم كل CSS أو App/Studio بالكامل. يوجد فصل لخدمات الشات والصوت والنظام والنماذج، مع بقاء المسارات العامة.
6. **حدود التنفيذ:** تشغيل اختبارات المشروع وبنائه ينفذ كود المشروع بعد الموافقة والمهلات وقيود المسار والبيئة. لم تُضف حاوية عزل لنظام Windows، ولم تُقاس سرعة نماذج حقيقية أو استهلاكها على جهاز المستخدم. اعتمادات Python الخاصة بـWindows ليست lockfile كاملًا مختبرًا على Windows.
7. **بيانات المستخدم:** لم تُقدّم قاعدة بيانات الاستخدام الفعلية أو مفاتيحه لاختبار ترقية نسخة شخصية. حُفظت المسارات والمعرفات القائمة، ونجحت اختبارات الحفظ والاستعادة والترحيل المتاحة؛ لا يوجد ادعاء بفحص بيانات لم تُرسل.
