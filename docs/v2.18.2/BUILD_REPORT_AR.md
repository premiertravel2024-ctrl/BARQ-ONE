# BARQ v2.18.2 — إصلاح WinError 32 أثناء self-test

28 أكتوبر 2026. حزمة سورس كاملة محدثة من v2.18.1. لا يوجد EXE أو مثبت جديد جرى اختباره في هذه البيئة.

## ما تثبته صورة Windows

سجل المستخدم يوضح أن PyInstaller أكمل إنشاء EXE وCOLLECT بنجاح، ثم توقف فحص الملف المجمد بسبب PermissionError [WinError 32] عند حذف brain.sqlite3 داخل مجلد barq-self-test المؤقت. نجاح إنشاء EXE لا يُعد نجاحًا للمثبت أو لاختبار التشغيل الكامل.

## السبب والإصلاح

`with sqlite3.connect(...)` في المكتبة القياسية ينهي المعاملة بـcommit أو rollback لكنه لا يغلق الاتصال. استخدمت مخازن BARQ هذا النمط، فبقي إغلاق بعض الملفات معتمدًا على توقيت جمع القمامة. Linux يسمح عادة بحذف ملف مفتوح، بينما Windows يمنع ذلك. كذلك كان Cache يحتفظ باتصال قاعدة بيانات ملفية طوال عمر الكائن.

أُصلح السبب في التطبيق نفسه:

- core/sqlite.py: استخدام Connection تُنهي المعاملة ثم تغلق الاتصال في finally، عند النجاح والفشل. يُغلق الاتصال أيضًا إذا فشلت تهيئة PRAGMA، ويُعاد الخطأ بدل إخفائه. WAL وbusy_timeout وforeign_keys تبقى مفعلة، ودعم قراءة قاعدة بيانات read-only محفوظ.
- cache/store.py: فتح اتصال ملفي لكل عملية وإغلاقه بعدها بدل اتصال دائم. المخطط ومفاتيح الكاش والبيانات القائمة لم تتغير. الوصول المتزامن محمي بقفل، والكاش في الذاكرة يبقى مدعومًا مع close صريح.
- coding/project_state.py: إغلاق الاتصال إذا أخفقت تهيئة مخطط قاعدة البيانات.
- desktop.py: التأكد من إغلاق خيط السيرفر في finally قبل انتهاء فحص التشغيل، وإضافة cleanup_completed=true فقط بعد انتهاء حذف المجلد المؤقت بنجاح. تقرير الفشل يوضح مرحلة الخطأ، ولا يحوّل خطأ التنظيف إلى نجاح.
- سكربتات التغليف وفحص المثبت والدليل النهائي تشترط نجاح التنظيف أيضًا. تم تحديث الإصدار والواجهة ومدخلات البناء إلى 2.18.2 وإعادة بناء React.

لم يُستخدم تجاهل PermissionError أو تعطيل self-test أو إجبار garbage collection كبديل لإغلاق الاتصالات.

## إثبات السلوك

أُضيفت tests/test_v2182_sqlite_lifecycle.py. قبل إصلاح التطبيق فشلت 11 حالة من أول 12 حالة، ومنها إعادة إنتاج رفض حذف قاعدة بيانات مفتوحة. أُضيفت لاحقًا 3 حالات إضافية، وأصبحت الحالات الـ15 كلها ناجحة بعد الإصلاح.

الاختبارات تحتفظ بمراجع قوية إلى اتصالات SQLite، ولذلك لا يمكن أن تنجح بسبب إغلاق عرضي من GC. تشمل:

- commit ثم إغلاق، وrollback ثم إغلاق دون فقد سلامة المعاملة.
- إغلاق اتصالات مخازن المهام والمحادثات والحصص والذاكرة الدلالية وملحوظات المشروع وفهرس التشغيل والكاش.
- كتابة متزامنة للكاش واستعادته بعد إعادة فتحه، واستمرار عمل الكاش في الذاكرة حتى close.
- إغلاق الاتصال عند فشل التهيئة، وإمكانية قراءة قاعدة بيانات read-only.
- تشغيل API وHTTP وخطة إنشاء مشروع والإغلاق الحقيقي في عملية فرعية، مع محاكاة قاعدة مشاركة ملفات Windows: يُرفض تنظيف المجلد إذا بقي اتصال مفتوح، حتى مع الاحتفاظ بكل الكائنات في الذاكرة. المتصفح الرسومي فقط مقلد في هذا الاختبار، وليس منطق SQLite أو API أو HTTP.
- اختبار منفصل يفرض فشل التنظيف، ويتأكد أن البرنامج يعيده كفشل حقيقي ولا يصدر status=ok.

## إعادة البناء

1. فك الحزمة الجديدة في مجلد سورس جديد وافتح مجلد BARQ بداخله.
2. شغّل BUILD_BARQ.bat من النسخة الجديدة. يجب إعادة تغليف EXE؛ نسخ ملفات Python بجانب EXE القديم أو إعادة self-test عليه لن يغير الكود المجمد بداخله.
3. لا تشغّل البناء من مجلد staging القديم الظاهر في الصورة، ولا تشغّل installer.iss منفردًا، ولا تتجاوز مرحلة smoke test.
4. النجاح الكامل سيُنتج release/BARQ_Setup_2.18.2.exe وBARQ_Portable_2.18.2.zip وعلامة build-ok-v2.18.2.marker بعد اجتياز جميع المراحل، مع self-test.json وinstalled-self-test.json اللذين يحتويان cleanup_completed=true.
5. لا تحذف %LOCALAPPDATA%\AI Router Agent أو مجلدات مشاريعك؛ بيانات التثبيت والإعدادات تظل في المسارات السابقة.

قائمة التغييرات الكاملة مقارنة بـv2.18.1 في CHANGED_FILES.md وCHANGED_FILES.json بجانب التقرير. تقارير وإثباتات v2.18 وv2.18.1 داخل الحزمة تاريخية. بصمات ملفات النسخة الحالية في SOURCE_MANIFEST_SHA256.json.
