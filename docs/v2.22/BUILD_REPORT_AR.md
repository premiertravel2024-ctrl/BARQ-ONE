# BARQ v2.22.0 — إصلاح توليد الملفات وبث الكود إلى مساحة العمل

هذه نسخة سورس كاملة مبنية على ملف `BARQ_v2.21_MISSION_CONTINUITY_STUDIO_REPAIR_FULL_SOURCE(1).zip` المرفق، وليست استبدالًا له بمشروع جديد. تاريخ التحقق: 28 أكتوبر 2026.

## السبب الذي ثبت بالكود والاختبار

مسار المهمة كان يطلب ردًا بصيغة `### FILE:` ويذكر عبارة `no JSON` في نفس التعليمات، لكنه يستدعي الراوتر دون عقد تحقق خاص بالملف. الفحص العام يرى كلمة JSON، فيحاول تحليل الكود كـJSON ويرفض ردًا صحيحًا. الاختبار الجديد يمر عبر Engine ومحول Ollama الحقيقيين، ويثبت أن الرد نفسه يرفضه الفحص القديم ويقبله عقد الملف الجديد.

كما كانت مساحة العمل تُفتح بعد انتظار طلب التحضير، ولم يكن هناك مسار يربط أجزاء الرد بواجهة المهمة. لذلك لم يكن انتظار المستخدم يعرض الكتابة الفعلية. وكانت المهمة تتوقف بعد حفظ الملفات وفحص الصياغة بدل الاستمرار للاختبار والبناء.

## ما تغير

- تحقق مستقل لرد الملف: مسار هدف ثابت، ملف كامل، فحص الصياغة، ورفض المسار المخالف أو الرد المقطوع. يقبل FILE أو سياج كود واحد، وبعض صيغ الكود الخام الصالحة، دون افتراض أن الكود JSON.
- بث أجزاء الرد الفعلية من Ollama NDJSON أو الواجهات المتوافقة مع OpenAI SSE إلى تبويب «كتابة برق». تُفتح مساحة العمل قبل انتظار التحضير. لا يوجد تحريك كتابة مصطنع، ولا حفظ تلقائي للأجزاء الناقصة.
- لمسار توليد المصدر فقط: طلب `think:false` من Ollama، وحد إخراج 8192، ووقت مستقل لتوليد الملف. يحتفظ الاختيار المحلي الصريح بخصوصيته، ولا يُنزّل نموذجًا ولا يتحول سرًا إلى السحابة. Auto يستطيع استخدام بدائل مسموحة ضمن الميزانية؛ لا يستهلك انتظار المحلي ميزانية البدائل السحابية كلها.
- سياق الملفات التالية يتضمن أجزاء محدودة من المصدر المحفوظ، وليس أسماء الدوال فقط، لتحسين توافق الاستيراد وتوقيعات الدوال.
- مهمة Python الجديدة تتضمن `test_app.py` لاختبار السلوك الفعلي. بعد الحفظ وفحص الصياغة تقترح تشغيل الاختبارات، ثم بناء EXE عند طلب Windows/EXE، داخل نفس المهمة ومع موافقة لكل تشغيل.
- نتائج الاختبار والبناء مرتبطة ببصمة الملفات. تعديل المصدر يبطل النتائج القديمة. الاختبار الفاشل يمرر مخرجاته للإصلاح، ولا يُعاد على نفس المدخلات تلقائيًا بلا تعديل.
- استكمال المهمة يحفظ ارتباطها بالمشروع عند التعطل. إعادة المحاولة تسمح بإعادة توليد ملف متعثر مع الاحتفاظ بعدد المحاولات والميزانية. تحديث المهام القديمة يضيف هدف الاختبارات دون إعادة توليد الملفات المحفوظة.
- التوقف يمسح حالة التحميل المحلية ويحتفظ بما حُفظ. سبب الملف يظل ظاهرًا في تقدم المهمة. لا يُنصح المستخدم بتشغيل Ollama وكأنه غير مستخدم أصلًا.
- مخرجات الأدوات والبناء ومسارات المنتجات تظهر في لوحة المخرجات. فحوص Git/GPU الخلفية تستخدم تشغيلًا بلا نافذة كونسول على Windows، مع الاحتفاظ بإخفاء كونسول الأدوات الموجود في النسخة المرفقة.
- بقاء الموافقات المنفصلة، رفض الكتابة قبل الموافقة، حماية مسودة المستخدم وتعارضات القرص، وربط أرقام إصدار المصدر والواجهة والبناء. تم الاحتفاظ بإصلاح `UsePreviousLanguage=no` وإغلاق SQLite قبل تنظيف اختبار التشغيل.

## التحقق

النتائج التفصيلية في `verification/v2.22/`:

- مجموعة Python/API: **867 اختبارًا ناجحًا و65 اختبارًا فرعيًا ناجحًا، دون فشل أو تخطٍ**، مع تقرير JUnit وسجل التنفيذ.
- TypeScript وVite: بناء React فعلي، لا مجرد فحص نصي.
- اختبارات تدفق الواجهة والاستيراد والشات والموافقات ومزامنة المحرر.
- متصفح Chromium مع React وFastAPI وعمليات ملفات حقيقية: ظهور أجزاء الكود قبل انتهاء الرد، فتح تبويب الكتابة تلقائيًا، منع تنفيذ المسودة الجزئية، مراجعة وحفظ منفصلان، وعدم تكرار الحفظ.
- اختبار خاص بنفس مسار Ollama المحلي المثبت على `qwen3:4b`: FILE مباشر ثم فشل توليد الملف التالي، مع إثبات توقف حالة الخادم والواجهة وبقاء الملف السابق.
- اختبار الموافقة بالنقر المزدوج، إغلاق البوب أب أثناء انتظار النموذج، تحديث المحرر بعد الحفظ، واشتراط موافقة جديدة للخطوة التالية.
- اختبار الحفاظ على المسودات والتعارضات والتراجع وفتح نتيجة البحث عند سطرها.
- دورة مهمة متعددة الملفات تمر من التوليد إلى تشغيل pytest فعلي داخل المشروع التجريبي ثم اقتراح بناء Windows؛ لا يُستخدم نجاح وهمي للاختبارات.
- اختبار تشغيل المصدر `desktop.py --self-test` مع خادم HTTP وواجهة React وتنظيف SQLite ناجح، وفحص اتساق المصدر والإصدار.

## الحدود التي لم تُختبر

لا يوجد Windows أو Ollama بنموذج حقيقي في بيئة التحقق. ردود النماذج مضبوطة للاختبار؛ هي تختبر الراوتر والنقل والتحقق والواجهة ولا تثبت جودة استدلال qwen3:4b على جهازك. لم يُبنَ أو يُشغَّل EXE/مثبت v2.22.0 هنا. قدرة النموذج والذاكرة وطول الطلب وتوفر أدوات المشروع ما زالت تؤثر على النجاح والسرعة؛ النسخة تعالج الأعطال المحددة ولا تضمن نجاح أي برنامج بأي حجم.

نجاح pytest أو إنتاج EXE لا يثبت تجربة كل وظيفة رسومية يدويًا. هذا التفريق يظهر في رسالة نهاية المهمة نفسها. إن كان PyInstaller أو اعتماد خاص بالمشروع مفقودًا، يظهر الخطأ الفعلي؛ لا تثبيت صامت للاعتمادات ولا تجاوز للموافقة.

يوجد تحذير إهمال من Starlette/httpx في بيئة الاختبار، وتحذيرا Vite عن حجم الحزمة والخط الاختياري غير المرفق. لا تمنع البناء. الخط البديل متاح؛ تفاصيل الترخيص في `SOURCE_FONT_NOTICE.txt`.

## تطبيق التحديث

1. أغلق برق، وفك ZIP كاملًا في مجلد جديد.
2. شغّل `BARQ/BUILD_BARQ.bat` على Windows. لا تشغّل `installer.iss` منفردًا ولا تعيد استخدام EXE قديم.
3. بعد نجاح المراحل، ثبّت `release/BARQ_Setup_2.22.0.exe`. واجهة «حول» يجب أن تعرض 2.22.0.
4. افتح مشروعك السابق من مساحة العمل واستكمل الطلب من المحادثة نفسها. احتفظ ببياناتك ومفاتيحك؛ لا تحتاج حذفها.
5. أثناء التوليد يظهر تبويب «كتابة برق». نافذة الموافقة تغلق فور قبول الخطوة، ويظهر طلب حفظ مستقل للفرق. نتائج الاختبارات والبناء تظهر في المخرجات.
